# Artifact   : security-audit/run-metadata.txt
# Layer      : cross-cutting. This file is not a findings artifact and carries no
#              severity, CWE or gateBlocking field. It records HOW the layers ran:
#              exact tool versions, acquisition provenance, exit codes, wall-clock
#              durations, counts, and every deviation or limitation encountered.
# Role       : the plan designates this file as the home for "tool self-reports
#              plus per-layer run statistics ... exact tool versions, scan exit
#              codes, wall-clock durations, files scanned". The pinned rule packs
#              additionally require their source URL, byte size, parsed stanza
#              count, the grep-vs-parse caveat, the authored-to-loaded delta and
#              the validation exit code to be recorded here.
# Pass rule  : GLOBAL RULE - no layer may silently fail. Every exit code below is
#              recorded with its meaning, including the NON-ZERO exit codes that
#              are benign, so that a later run cannot misread a normal result as
#              a failure or a failure as a normal result.
#              verification check 12 - contains no ANSI escape byte (ESC, 0x1B).
# Scope      : read-only assessment. No application source file is modified, no
#              dependency is installed, and no vulnerability is remediated. No
#              live, deployed or remote target of the audited product is
#              contacted. The only network egress is to the public Semgrep rule
#              registry (semgrep.dev) to fetch the three pinned rule packs, and
#              to the OSV database for Layer 4; both are required by the plan.
# Format     : plain UTF-8, LF line endings, ASCII-only payload, comment lines
#              prefixed '#'. Every REPOSITORY path recorded here is
#              repository-relative, so no artifact content is host-specific and
#              this file is portable across checkouts.
#              ONE DELIBERATE EXCEPTION, stated rather than glossed: the absolute
#              paths of the HOST ANALYSIS BINARIES are recorded on purpose -
#              /opt/venvs/security-audit (semgrep) and /usr/local/bin/osv-scanner -
#              because practice E10 requires traceable tool provenance and a
#              binary's identity is meaningless without its location and digest.
#              These are tool locations on the execution host, never repository
#              content, and nothing downstream consumes them as paths. A blanket
#              claim that no host-specific path appears anywhere in this file
#              would be false, and stating it accurately costs nothing.
# Secrets    : no secret value is recorded here. Where a high-entropy value was
#              discovered during discovery it is cited by file, line, character
#              class and length only, never by value.

# =============================================================================
# SECTION 6 - CONTENT NEGOTIATION: WHY Accept-Encoding MUST BE PINNED
# =============================================================================
# The pack URLs return DIFFERENT DOCUMENTS depending on the encodings the client
# advertises. This was measured on the command line and independently
# corroborated in a real headless browser. It is the reason the acquisition
# command pins 'Accept-Encoding: identity' rather than relying on a default.

# ---- measured representations of https://semgrep.dev/c/p/owasp-top-ten ------
# request Accept-Encoding      content-type              enc      content-length  body begins
# --------------------------  ------------------------  -------  --------------  ------------
# identity (pinned, ours)     text/yaml; charset=utf-8  none     1448110         rules:
# <no header sent> (curl dflt) text/yaml; charset=utf-8  none     1448110         rules:
# gzip, deflate, br           application/json          gzip     ABSENT          gzip bytes
# gzip via curl --compressed  application/json          gzip     ABSENT          {"rules":[
# browser-like (real Chrome)  application/json          gzip     ABSENT          {"rules":[

# ---- what the JSON representation actually is -------------------------------
# It encodes the SAME 560 rule stanzas, but it is not the pinned document:
#   - top-level keys are ['rules','missed'] rather than ['rules'] alone
#   - 'missed' is an integer: 1800 for owasp-top-ten, 218 for secrets
#   - uncompressed size is 1306540 bytes, not 1448110
#   - it carries a DIFFERENT ETag from the YAML representation
#   - 'vary: Accept-Encoding' is emitted ONLY on the JSON variant, which is
#     direct server-side evidence of branching on the request header
# The two representations are therefore NOT interchangeable: they differ in
# media type, byte count, ETag and top-level schema.

# ---- honest scoping of the risk (this is a latent hazard, not a live break) --
# curl sends NO Accept-Encoding header unless asked, and the origin treats that
# as identity. The previously delivered command therefore DID receive correct
# YAML on this host. The hazard is that correctness was incidental rather than
# guaranteed: any gzip-advertising client silently receives the JSON document
# instead. That includes every browser, curl --compressed, and the default
# configuration of most HTTP libraries and some intermediary proxies. Pinning
# the header converts an incidental success into a guaranteed one.

# ---- browser corroboration (independent client, independent operator) -------
# A real headless Chrome navigation to both pack URLs returned, for the main
# document: status 200, content-type application/json, content-encoding gzip,
# NO content-length, vary: Accept-Encoding, and a body beginning {"rules":[ with
# top-level keys ['rules','missed'].
# Two further facts were established that strengthen the requirement:
#   1. 'Accept-Encoding' is a FORBIDDEN HEADER NAME in the Fetch standard. A
#      browser CANNOT request the identity representation from script: the header
#      is stripped silently from the Request object with no exception and no
#      console warning, and the request goes out advertising gzip regardless.
#      A browser therefore has no way to obtain the pinned YAML document.
#   2. The browser's received bytes were digest-identical to a gzip-advertising
#      command-line capture, and digest-DIFFERENT from the identity capture.
# Cross-client integrity check: the browser operator's own independent identity
# fetch of the owasp-top-ten and secrets packs produced bodies whose digests
# match the pinned on-disk packs EXACTLY. Pack integrity is therefore confirmed
# by two independent HTTP clients, not one.

# =============================================================================
# SECTION 9 - THE CANONICAL DIGEST ALGORITHM (specified so it is reproducible)
# =============================================================================
# A digest that is invariant to stanza order is only meaningful if the algorithm
# is stated exactly. Two plausible variants disagree with each other, so the
# choice is recorded explicitly rather than left implicit.
#
# ALGORITHM (authoritative):
#   1. Parse the pack with a YAML safe loader; take the top-level 'rules' list.
#   2. Serialise EACH rule independently to JSON with:
#        sorted object keys, no whitespace between tokens, Unicode not escaped.
#   3. SORT THE RESULTING SERIALISED STRINGS lexicographically.
#   4. Join them with a single newline between entries.
#   5. SHA-256 the UTF-8 encoding of that joined text.
#
# WHY THIS VARIANT: sorting the serialised STRINGS is order-insensitive by
# construction. The rejected variant - sorting the rule objects by their 'id'
# field before serialising - yields a different digest and additionally depends
# on identifiers being unique and on a tie-break rule. Identifiers happen to be
# unique within each pack here (0 intra-pack duplicates, verified per pack), but
# the algorithm must not rely on a property that upstream does not guarantee.
# Both variants were computed; both are stable pinned-vs-upstream; the specified
# one is authoritative and is the value recorded in SECTION 8.

# ---- rule-identifier prefix stability (the reason the config path is relative) -
# Semgrep derives each rule identifier from the configuration path by replacing
# separators with dots and dropping any leading separator. It is NOT the
# directory basename. With the relative path 'security-audit/rules' every loaded
# rule carries the prefix 'security-audit.rules.', which is host-independent and
# therefore stable across checkouts. An absolute configuration path would embed
# the host path into all 725 identifiers and would break the SARIF severity join,
# the cross-layer deduplication key and every baseline diff.

# CONTROL 2 (F8) - PATH-SAFE ATOMIC ARTIFACT WRITER
# =============================================================================
# Contract: every artifact published into security-audit/ is written through a
# verified-root, no-follow, exclusive-temporary, fsynced, atomically renamed path.
# No artifact is ever written by plain shell redirection into the ignored tree again.
#
# PROTOCOL (in order; any failure aborts the write and leaves the previous artifact
# untouched):
#   1. Pin and resolve the repository root once. Refuse an absolute target path,
#      refuse any ".." component, and refuse a target whose lexical join escapes the
#      pinned root - containment is checked BEFORE any filesystem access.
#   2. lstat every path component from the root down: refuse a symlink anywhere on the
#      chain, refuse a non-directory intermediate component, and - when the target
#      already exists - refuse a non-regular file or st_nlink != 1.
#   3. Refuse the payload outright if it carries an ANSI escape byte. Redaction and
#      ANSI stripping are CAPTURE-STAGE transforms (IR4), so the writer is the last
#      place they can be enforced rather than a later cleanup pass.
#   4. Open a same-directory temporary with O_CREAT|O_EXCL|O_WRONLY|O_NOFOLLOW
#      (plus O_CLOEXEC). O_EXCL is what makes a squatted temporary name a refusal
#      instead of a clobber; O_NOFOLLOW is what makes a symlinked temporary name a
#      refusal instead of a redirect.
#   5. Write, flush, fsync the file descriptor, and assert the written size.
#   6. Read the temporary back and compare its SHA-256 to the intended payload.
#   7. chmod to 0644, then os.rename onto the target - a single atomic operation, so a
#      reader never observes a partial artifact and no window exists between validate
#      and publish (this is the CWE-367 half of the finding).
#   8. fsync the containing DIRECTORY so the rename itself is durable.
#   9. Re-verify the published inode: regular file, st_nlink == 1, digest as intended.
#  10. On any exception, unlink the temporary so no partial file is left behind for a
#      later run to trip over.
